# Image Storage API

REST API for secure image upload, storage, compression, and deduplication.
Built with Laravel 11, PostgreSQL, Redis, MinIO (S3-compatible), and Laravel Horizon.

---

## Features

| Feature | Details |
|---------|---------|
| Authentication | Register, login, logout via Laravel Sanctum (Bearer tokens) |
| Upload | PNG and JPEG only, max 5 MB per file |
| Async processing | 202 accepted immediately; compression + S3 upload run in background |
| WebP compression | Every image converted to WebP at 80% quality (~35% smaller than JPEG) |
| Deduplication | Identical files (same SHA-256 hash) share one S3 object — no redundant uploads |
| Ownership isolation | Users can access only their own images |
| Rate limiting | 120 uploads/min per IP, 10 000 uploads/day per user |
| Queue scaling | Horizon auto-scales up to 30 upload workers — handles 1 M+ uploads/day |

## Installation

```bash
# 1. Clone the repository
git clone https://github.com/sardorjs/dmed-tz.git
cd dmed-tz

# 2. Copy environment file
cp .env.example .env

# 3. Build images, start containers, install dependencies,
#    run migrations, create MinIO bucket, start Horizon workers
make setup
```

The application is ready at **http://localhost**.

### What `make setup` does step by step

1. Builds Docker images
2. Starts all containers (app, nginx, postgres, redis, minio)
3. Waits for each container to become healthy
4. Runs `composer install`
5. Generates `APP_KEY`
6. Runs database migrations
7. Creates the `dmed` bucket in MinIO
8. Starts Laravel Horizon (queue workers)

### Images

#### Upload image

```
POST /api/images
Content-Type: multipart/form-data
```

*Requires authentication.*

| Field | Type | Rules |
|-------|------|-------|
| `image` | file | required, PNG or JPEG, max 5 MB |

The image is saved to temp storage, a DB record is created, and a background job is dispatched. The response reflects the initial `pending` state — poll `GET /api/images/{id}` or check the list to confirm `done`.

**Response `202 Accepted`:**

```json
{
  "data": {
    "id": 42,
    "name": "photo.png",
    "status": "pending",
    "url": null,
    "size": 204800,
    "mime_type": "image/png",
    "created_at": "2026-02-19T12:00:00.000000Z"
  }
}
```

After the background job completes, `status` → `done` and `url` is populated.

**Response `422 Unprocessable`:**

```json
{
  "message": "The image field must be a file of type: png, jpg, jpeg.",
  "errors": {
    "image": ["The image field must be a file of type: png, jpg, jpeg."]
  }
}
```

**Response `429 Too Many Requests`** — rate limit exceeded.

---

#### List images

```
GET /api/images
```

*Requires authentication. Returns only the authenticated user's images, newest first.*

**Response `200 OK`:**

```json
{
  "data": [
    {
      "id": 42,
      "name": "photo.png",
      "status": "done",
      "url": "http://localhost:9010/dmed/images/abc123.webp",
      "size": 204800,
      "mime_type": "image/webp",
      "created_at": "2026-02-19T12:00:00.000000Z"
    }
  ]
}
```

---

#### Get image

```
GET /api/images/{id}
```

*Requires authentication. Returns `404` if the image belongs to another user.*

**Response `200 OK`:** single image object (same fields as list item).

**Response `404 Not Found`:**

```json
{ "message": "Resource not found." }
```

---

#### Delete image

```
DELETE /api/images/{id}
```

*Requires authentication. Returns `404` if the image belongs to another user.*

Ownership is validated synchronously. The actual S3 deletion runs in a background job.

**Response `202 Accepted`:**

```json
{ "message": "Image is being deleted." }
```

---

### Image status reference

| Status | Meaning |
|--------|---------|
| `pending` | Saved to server, waiting in the queue for S3 processing |
| `done` | Compressed, uploaded to S3 — `url` is available |
| `failed` | Processing failed after 3 retries with exponential backoff |

## Architecture

```
Client
  │
  ▼
Nginx (port 80)
  │
  ▼
PHP-FPM  ──►  UploadImageUseCase
                    │
                    ├─ putFile → local temp storage
                    ├─ hash_file('sha256', ...) → compute SHA-256
                    ├─ INSERT images (status=pending)
                    └─ dispatch ProcessImageUploadJob → Redis
                    │
              ◄─── 202 Accepted
  │
  └─── Laravel Horizon workers
             │
             ▼
       FinalizeImageUploadUseCase
             │
             ├─ Dedup: hash already done? ──► reuse S3 path
             │
             └─ GD: read PNG/JPEG → encode WebP (q=80) → tmp file
                          │
                          ▼
                   S3 / MinIO  ◄── putFile('images/', webp)
                          │
                          ▼
                  UPDATE images (status=done, mime=image/webp)
```

### Queue supervisors

| Supervisor | Queue | Min | Max | Job type |
|------------|-------|-----|-----|----------|
| `supervisor-upload` | `images-upload` | 5 | 30 | Compress + S3 upload |
| `supervisor-delete` | `images-delete` | 2 | 10 | S3 delete |
| `supervisor-default` | `default` | 1 | 5 | Other |

Horizon uses the `time` auto-scaling strategy — workers scale to minimise wait time.

### Deduplication

1. SHA-256 hash is computed from raw file bytes at upload time (stream-based, no full memory load).
2. The processing job queries for an existing `done` image with the same hash.
3. If found — the new DB record gets the same S3 path. No upload performed.
4. At deletion — the S3 object is only removed when no other DB record references the same path.

### Compression

Images are converted to **WebP at 80% quality** using PHP's built-in GD extension.
Average size reduction: ~35% vs JPEG at equivalent visual quality.
The `mime_type` field in the API response reflects the stored format (`image/webp`).

## Running tests

```bash
make test
```

Or directly:

```bash
docker exec dmed-app php artisan test
```

Test environment:
- `RefreshDatabase` — each test starts with a clean database
- `Storage::fake('local')` — no real S3 writes, files stored in a temp directory
- `QUEUE_CONNECTION=sync` — jobs run inline so the full pipeline (upload → compress → storage) is covered
